# 术语分册：大模型与 Agent

> 用户方向里的第三块。这册的重点是：什么时候该用大模型、它能替代什么、不能替代什么。
> 每行 = 术语 | 一句话定义 | 生活化比喻 | 在 PHM 语境下怎么用。

| 术语 | 一句话定义 | 生活化比喻 | 在 PHM 语境下怎么用 |
|---|---|---|---|
| 大语言模型（LLM） | 在海量文本上预训练的通用序列生成模型 | 读遍图书馆、但没进过车间的实习生 | 写诊断报告、解释报警、检索文献、生成实验脚本 |
| 词元（Token） | 模型处理的最小文本单位，约等于一个词或半个词 | 把句子切成积木块 | 成本与上下文长度都按 token 计 |
| 上下文窗口（Context Window） | 一次能"看进眼里"的最大 token 数 | 一张桌子的桌面大小 | 放不下整篇长论文全文，需要分段或检索 |
| 提示（Prompt） | 给模型的指令与示例 | 给实习生的任务说明书 | 少样本示例能显著改善输出格式与术语一致性 |
| 思维链（Chain-of-Thought） | 让模型先写推理过程再给结论 | 要求先列算式再写答案 | 让模型逐步解释"为什么判成内圈故障"，便于核查 |
| 温度（Temperature） | 控制输出随机性，越低越确定 | 考生答题的"保守/发散"程度 | 生成诊断报告要低温度；头脑风暴要高温度 |
| 幻觉（Hallucination） | 模型一本正经地编造不存在的事实/文献 | 自信的胡说八道 | 诊断结论、引用必须回到原论文核对，不能信模型自述 |
| 检索增强生成（RAG） | 先从知识库检索，再把检索结果塞进提示让模型回答 | 开卷考试：先翻书再答题 | 把维修手册、历史工单、论文片段做成检索库再问答 |
| 嵌入（Embedding） | 把文本/信号映射成向量，语义近的向量近 | 把内容换算成"坐标" | 故障描述相似检索、工单聚类 |
| 向量数据库（Vector DB） | 专门存向量并做近邻检索的库 | 按"意思"而不是按"字面"排架的书架 | 历史案例检索、相似故障推荐 |
| 工具调用（Tool / Function Calling） | 模型输出结构化调用请求，由外部程序执行 | 让实习生操作机床而不是空口描述 | 让 agent 去跑 FFT、查数据库、画图、写文件 |
| 智能体（Agent） | 能自己规划步骤、调用工具、迭代直到完成目标的系统 | 会自己排工序的工人 | 从"给一篇论文"到"出精讲 + 校验 + 导出"全自动 |
| ReAct（推理-行动循环） | 思考一步 → 行动一步 → 观察结果 → 再思考 | 边做边看反馈，不一次憋到底 | 多步故障排查：查手册→提假设→看数据→修正 |
| 规划（Planning） | 把大目标拆成可执行子任务 | 先写施工计划再开工 | 长任务（精讲整篇论文）拆成取全文/拆节/校验 |
| 记忆（Memory） | 跨轮次保存上下文与结论的机制 | 会议纪要 | 多轮追问时不必重复已确认的论文信息 |
| 多智能体（Multi-Agent） | 多个角色分工协作（检索员、审稿员、写手） | 一个小组各司其职 | 一个写、一个挑错、一个核对公式，互相制衡 |
| 指令微调（Instruction Tuning） | 用"指令-回答"对训练模型听指令 | 岗前培训，学会按要求干活 | 让模型稳定输出 10 节结构而不跑题 |
| LoRA / 参数高效微调 | 只训练少量附加参数来适配新任务 | 给通用工具加几个专用配件 | 低算力下让模型适配"故障诊断精讲"这一任务 |
| 量化（模型侧） | 把权重压成低精度以省显存 | 把高清图压成缩略图 | 边缘端部署小模型时的常规操作 |
| 评测基准（Benchmark） | 用固定题集比较模型能力 | 统一考卷 | 论文若报 LLM 效果，先看它用的是哪套卷子、是否自建 |
| 对齐 / 安全（Alignment） | 让模型行为符合人类意图与规范 | 员工守则 | 医疗/工业场景里，模型不该给出无依据的处置建议 |

## 数字例子模板（RAG 的检索命中）

知识库 3 条：A"内圈故障频谱出现 BPFI 及谐波"、B"外圈故障出现 BPFO"、C"润滑不足导致温升"。
查询"滚珠通过内圈的频率"，与 A 的向量相似度 0.91、B 0.42、C 0.18。
取 top-1 = A 塞进提示，模型据此回答 BPFI（Ball Pass Frequency Inner）。
**读法**：RAG 的价值不在模型变聪明，而在"答案有出处"；相似度阈值定低了会把无关文档喂进去，反而诱发幻觉。
